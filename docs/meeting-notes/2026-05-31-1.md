## 논의 내용

DB 부하 감소를 위해 Redis를 도입하는 방안을 검토하고 구현 계획을 수립했다.

---

## 문제 인식

기존 구조는 Wikipedia edit 이벤트가 발생할 때마다 SQLite(SSD)에 즉시 write한다.
SSD는 빈번한 write에 적합하지 않으며, 1회성 편집처럼 분석에 불필요한 이벤트까지 모두 저장되는 문제가 있다.

---

## 결정 사항

### Redis 데이터 구조

| Key | 타입 | 용도 |
|-----|------|------|
| `edits:{title}` | Sorted Set | 이벤트 ring buffer (score=timestamp) |
| `stats:{title}` | Hash | article_stats 현재값 |
| `stats:index` | Sorted Set | 전체 타이틀 목록 (score=last_seen_at) |

- `edits:{title}` 는 max_size 초과 시 oldest eviction. TTL 없음.
- max_size는 1시간 분량의 타이틀당 평균 편집 수 기준으로 산정.
- 타이틀별 ring buffer 채택 — 전역 버퍼 대비 구현 단순, `find_by_title` 효율 유지.

### SQLite write 트리거

| 시점 | 동작 |
|------|------|
| count == 3 도달 | edit_events 3개 소급 flush + article_stats flush |
| count > 3 | 매 이벤트마다 edit_event write + article_stats update |
| ring buffer eviction | SQLite 직접 조회 → 있으면 누적, 없으면 버림 |

- `edit_velocity`, `revert_count` 는 SQLite 기존 값에 누적.
- `tension_score`, `status`, `flags` 는 현재 윈도우 값으로 덮어쓰기.

### 역할 분리

- Redis: 1시간 윈도우 분석의 primary store (RAM)
- SQLite: 3회 이상 편집된 문서의 영구 아카이브 (SSD)
- Dashboard: `get_all_stats` 를 SQLite 대신 Redis에서 읽도록 변경

## 구현 범위

**변경 파일**

- `pyproject.toml` — `redis` 패키지 추가
- `storage.py` — Redis 함수 추가 (기존 SQLite 함수 유지)
- `coordinator.py` — redis 파라미터 추가, read/write 경로 교체
- `dashboard.py` — `get_all_stats` Redis로 교체
- `main.py` — Redis 연결 생성 및 Coordinator 주입

**추가 함수 (`storage.py`)**

- `redis_save_event` — ZADD + eviction 처리
- `redis_find_by_title` — ZRANGEBYSCORE
- `redis_upsert_stats` — HSET + stats:index 갱신
- `redis_get_all_stats` — stats:index 순회
- `flush_title_to_sqlite` — count==3 시 소급 flush
- `accumulate_stats_to_sqlite` — eviction 시 누적 write

**구현 순서**

1. `pyproject.toml`
2. `storage.py`
3. `coordinator.py`
4. `dashboard.py`
5. `main.py`
