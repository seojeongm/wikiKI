## 논의 내용

Wikimedia EventStreams API를 통해 실시간 편집 데이터를 수신하고, 긴장도 점수를 계산해 대시보드에 표시하는 시스템의 클래스 구조를 논의했다.

**클래스 구성**

- `StreamReceiver`: SSE 스트림 연결/해제/재연결 담당. `stream_with_reconnect()`로 이벤트를 제너레이터 방식으로 yield.
- `EditEvent`: 편집 이벤트 단위 객체. API 실제 필드(`title`, `user`) 사용. `isRevert`는 comment 파싱으로 내부 감지.
- `Coordinator`: 전체 흐름 조율. 스트림 수신 → 룰 평가 → 저장 → 스코어링 → 대시보드 업데이트 순서로 실행. persistence 책임은 여기서 담당.
- `RuleEngine`: 등록된 Strategy 목록을 순회하며 `Flag[]` 반환. 저장/스코어링 책임 없음.
- `Strategy` (interface) — 각 룰의 공통 인터페이스. `evaluate(event) Flag` 하나만 정의.
- `ThreeRRStrategy` / `VelocitySpikeStrategy` / `EditorConflictStrategy` / `NewAccountStrategy` — Strategy 구현체. 각각 3RR 위반, 편집 속도 급증, 편집자 충돌, 신규 계정 감지.
- `Flag`: 전략이 생산하는 값 객체. `type`, `weight`, `detectedAt` 포함.
- `TensionScorer`: `Flag[]`를 받아 긴장도 점수 계산 및 상태 문자열(`escalating` 등) 반환.
- `ArticleRepository`: 편집 이벤트 저장 및 조회. DB 연결은 private.
- `ArticleStats`: 대시보드 표시용 값 객체. 긴장도 점수, 편집 속도 등 집계 결과 보관.
- `Dashboard`: `ArticleStats` 목록을 렌더링. 상위 긴장도 문서 정렬 및 전체 통계 제공.

**Strategy 패턴 채택 이유**

룰을 클래스 단위로 분리해 `RuleEngine`을 수정하지 않고 새 전략을 추가할 수 있도록 했다. 향후 `BLPStrategy`, `SemiProtectedStrategy` 등 신규 룰 추가 시 기존 코드에 영향 없음.

**주요 논점**

- `EditEvent` 필드명을 API 실제 응답(`title`, `user`)에 맞게 수정. `articleId`는 사용하지 않음.
- `isRevert`는 raw 이벤트에 직접 포함되지 않아 `detectRevert(comment, rev)` private 메서드로 내부 처리.
- `RuleEngine`이 직접 repository에 쓰는 구조는 관심사 분리 원칙에 어긋나 `Coordinator`로 책임 이전.
- 옵저버 콜백 패턴(`onEditEvent`) 대신 제너레이터 패턴(`stream_with_reconnect`)으로 통일.

---

## 결정 사항

- Strategy 패턴으로 룰 엔진 구현. 신규 룰은 `Strategy` 인터페이스 구현체로 추가.
- `EditEvent` 필드는 Wikimedia API 응답 기준으로 고정 (`title`, `user`).
- Persistence 책임은 `Coordinator`가 단독 담당. `RuleEngine`은 평가만 수행.
- 스트림 처리는 제너레이터 패턴(`stream_with_reconnect`)으로 통일.
- 위 클래스 다이어그램을 MVP 구현 기준으로 확정.
