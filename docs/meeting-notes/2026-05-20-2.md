## 논의 내용

단일 편집 이벤트가 스트림에서 수신된 후 대시보드에 반영되기까지의 전체 흐름을 시퀀스 다이어그램으로 정리했다.

**흐름 요약**

- `StreamReceiver`: SSE 스트림에서 편집 이벤트를 수신해 `Coordinator`로 yield.
- `Coordinator`: 전체 흐름 조율. 저장 → 룰 평가 → 스코어링 → 대시보드 업데이트 순서로 실행.
- `ArticleRepository`: 이벤트를 DB에 저장. 룰 평가 전에 먼저 저장해 데이터 유실 방지.
- `RuleEngine`: 등록된 Strategy를 순회하며 `Flag[]` 반환.
- `Strategy`: 각 룰 구현체(`ThreeRR`, `VelocitySpike`, `EditorConflict`, `NewAccount`). `RuleEngine`이 루프로 호출.
- `TensionScorer`: `Flag[]`를 받아 긴장도 점수와 상태 문자열 반환.
- `Dashboard`: `Coordinator`로부터 완성된 `ArticleStats`를 받아 렌더링만 수행.

**Strategy 패턴**

`RuleEngine`은 등록된 Strategy 목록을 순회하며 각각 `evaluate(event)`를 호출한다. 시퀀스상 `ST`가 단일 참여자로 표현되지만 실제로는 복수의 구현체가 순차 호출된다. 신규 룰 추가 시 기존 흐름 변경 없이 구현체만 추가하면 된다.

**주요 논점**

- `Dashboard`가 렌더링 시점에 `ArticleRepository`를 직접 조회하는 구조는 불필요하다. `Coordinator`가 이미 완성된 `ArticleStats`를 전달하므로 대시보드는 받은 데이터를 표시만 하면 된다.
- 특정 문서의 편집 히스토리 드릴다운 기능은 MVP 범위 밖이므로 별도 흐름으로 추후 분리.
- `save(event)` 순서를 룰 평가 앞으로 이동. 평가 중 오류 발생 시에도 이벤트 자체는 보존.

---

## 결정 사항

- `Dashboard`는 `ArticleRepository` 직접 조회 없이 `Coordinator`로부터 받은 `ArticleStats`만으로 렌더링.
- `save(event)`는 룰 평가 이전에 실행. 데이터 유실 방지 원칙 적용.
- Strategy 패턴 유지. 신규 룰은 `Strategy` 인터페이스 구현체 추가로만 확장.
- 위 시퀀스 다이어그램을 MVP 구현 기준으로 확정.
